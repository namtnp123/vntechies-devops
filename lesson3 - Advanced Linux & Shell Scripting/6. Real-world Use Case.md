# Lesson 3: Real-world Use Case - "The Monday-morning web server check"

## Scenario

You are the new DevOps engineer. The company runs one Ubuntu server with nginx.
Every week the same things happen:

| Problem | Who complains | What you need to do |
|---|---|---|
| "The website is slow / returning errors" | Developers | Look at the nginx access log: who is hitting us, which URLs fail? |
| "Server disk is full, site is down" | Everyone, at 3am | Find what is eating the disk before it hits 100% |
| "We lost the nginx config after a bad change" | Your manager | Have a daily backup, and delete old ones so the backup does not fill the disk |
| "nginx / ssh crashed overnight" | Customers | Detect a stopped service and restart it automatically |

Doing this by hand means typing 20+ commands every time. We turn them into one script
([ops-toolkit.sh](ops-toolkit.sh)) and let **cron** run it.

## Setup (on the lab VM)

```bash
sudo apt install -y nginx
cp ops-toolkit.sh ~/ && chmod +x ~/ops-toolkit.sh

# Generate some traffic so the log has data
for i in $(seq 1 200); do curl -s -o /dev/null localhost/; done
for i in $(seq 1 30);  do curl -s -o /dev/null localhost/wp-login.php; done   # 404s, like a bot scan

sudo ~/ops-toolkit.sh logs        # reading /var/log/nginx needs root (or adm group)
```

## Step 1: do it by hand first (the commands you will use in real life)

Show students the one-liners before the script. Each one is a pipeline.

```bash
# Total requests, and how many were server errors (5xx)
wc -l < /var/log/nginx/access.log
grep -cE '" 5[0-9]{2} ' /var/log/nginx/access.log

# Status code distribution
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn

# Top 5 IPs hitting the server
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -5

# Which URLs return 404? (bots scanning for /wp-login.php, /.env ...)
awk '$9 == 404 {print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head

# Watch live, only errors
tail -f /var/log/nginx/error.log
tail -f /var/log/nginx/access.log | grep --line-buffered ' 500 '

# Disk: which filesystem is full, and which directory is the culprit?
df -h
sudo du -xh --max-depth=1 /var | sort -rh | head
sudo find /var/log -type f -size +100M

# Backup, verify, rotate
tar -czf ~/backup-$(date +%F).tar.gz /etc/nginx /var/www
tar -tzf ~/backup-$(date +%F).tar.gz > /dev/null && echo "backup OK"
find ~/backups -name 'backup-*.tar.gz' -mtime +7 -delete

# Service check
systemctl is-active nginx
sudo systemctl restart nginx
journalctl -u nginx -n 50 --no-pager
```

> Key idea: **`awk` pulls a column, `sort | uniq -c | sort -rn` counts and ranks.**
> That one pattern answers 80% of log questions.

### Flag reference: what every option means

Combined flags are just single-letter flags written together: `-cE` is `-c -E`.

**Reading and searching**

| Command | Flag | Meaning |
|---|---|---|
| `grep -cE '" 5[0-9]{2} ' file` | `-c` | **c**ount matching lines and print the number instead of the lines |
| | `-E` | **E**xtended regex, so `{2}`, `+`, `\|` and `()` work without backslashes |
| | `'" 5[0-9]{2} '` | Pattern: a quote, a space, `5`, any two digits (500-599), a space. This matches the status code in `"GET / HTTP/1.1" 500 512` |
| `grep --line-buffered ' 500 '` | `--line-buffered` | Print each match immediately. Without it, grep holds output in a buffer when piped, so `tail -f \| grep` looks frozen |
| `wc -l < file` | `-l` | Count **l**ines. `<` feeds the file in, so the output is just the number (no filename) |
| `tail -f file` | `-f` | **f**ollow: keep the file open and print new lines as they are written (Ctrl+C to stop) |
| `head -5` | `-5` (same as `-n 5`) | Show only the first 5 lines |
| `awk '{print $9}'` | `$9` | The 9th whitespace-separated column. `$1` is the first, `$NF` the last |
| `awk '$9 == 404 {print $7}'` | `$9 == 404` | A filter: only run `print $7` on lines where column 9 equals 404 |
| `awk -v limit=100 '...'` | `-v` | Pass a shell value into awk as a **v**ariable |

**Counting and ranking**

| Command | Flag | Meaning |
|---|---|---|
| `sort \| uniq -c \| sort -rn` | `uniq -c` | **c**ount how many times each line repeats (uniq only merges *adjacent* duplicates, so always `sort` first) |
| | `sort -r` | **r**everse order (largest first) |
| | `sort -n` | **n**umeric sort (so 10 comes after 9, not after 1) |
| | `sort -h` | **h**uman-numeric: understands sizes like `4.0K`, `20M`, `1G` |

**Disk and files**

| Command | Flag | Meaning |
|---|---|---|
| `df -h` | `-h` | **h**uman-readable sizes (`20G` instead of `20971520`) |
| `df -hP` (in the script) | `-P` | **P**OSIX format: one line per filesystem, never wrapped, safe to parse with awk |
| `du -xh --max-depth=1 /var` | `-x` | Stay on one filesystem (don't cross into other mounts) |
| | `-h` | Human-readable sizes |
| | `--max-depth=1` | Only show the directory's direct children, not every nested folder |
| `find /var/log -type f -size +100M` | `-type f` | Only regular **f**iles (`d` = directories) |
| | `-size +100M` | Bigger than 100 MB (`-100M` = smaller than) |
| `find ... -mtime +7 -delete` | `-mtime +7` | **m**odified more than 7 days ago (`-7` = within the last 7 days) |
| | `-name 'backup-*.tar.gz'` | Match the file name pattern. Quote it so the shell doesn't expand `*` first |
| | `-delete` | Delete the matches. **Run without `-delete` (or with `-print`) first to preview** |

**Backup**

| Command | Flag | Meaning |
|---|---|---|
| `tar -czf out.tar.gz dir/` | `-c` | **c**reate an archive |
| | `-z` | compress with g**z**ip |
| | `-f` | the next argument is the **f**ile name (always last in the group) |
| `tar -tzf out.tar.gz` | `-t` | lis**t** the contents without extracting. If it succeeds, the archive is readable |
| `tar -xzf out.tar.gz -C /tmp/x` | `-x` / `-C` | e**x**tract / change into directory first |
| `date +%F_%H%M%S` | `+%F` | `+FORMAT` prints a custom format: `%F` = `2026-11-10`, `%H%M%S` = `144128` |

**Services and logs**

| Command | Flag | Meaning |
|---|---|---|
| `systemctl is-active --quiet nginx` | `--quiet` | Print nothing, only set the exit code (0 = running). Perfect inside an `if` |
| `journalctl -u nginx -n 50 --no-pager` | `-u` | Show logs for one **u**nit (service) |
| | `-n 50` | Last 50 lines |
| | `--no-pager` | Print straight to the terminal instead of opening `less` |
| `curl -s -o /dev/null localhost/` | `-s` | **s**ilent: hide the progress bar |
| | `-o /dev/null` | Send the response body to `/dev/null` (discard it) |

**Cron and debugging**

| Command | Flag | Meaning |
|---|---|---|
| `sudo crontab -e` | `-e` | **e**dit the crontab (`-l` = **l**ist, `-r` = **r**emove all, careful!) |
| `>> file 2>&1` | `>>` | Append stdout to the file (`>` would overwrite) |
| | `2>&1` | Send stderr (2) to the same place as stdout (1), so errors are logged too |
| `bash -x script.sh` | `-x` | Trace: print every command before it runs |
| `bash -n script.sh` | `-n` | Syntax check only, don't run |
| `tee -a file` (in the script) | `-a` | **a**ppend instead of overwriting |

## Step 3: run it

```bash
sudo ./ops-toolkit.sh logs 10     # report, top 10
sudo ./ops-toolkit.sh disk
sudo ./ops-toolkit.sh services
sudo ./ops-toolkit.sh backup
ls ~/backups
cat ~/ops-toolkit.log

# Test the service watchdog
sudo systemctl stop nginx
sudo ./ops-toolkit.sh services    # should detect, restart and report
```

Try a low threshold so the disk warning fires during the demo:

```bash
DISK_THRESHOLD=10 ./ops-toolkit.sh disk
```

## Step 4: schedule it with cron

```bash
sudo crontab -e
```

```cron
# m   h  dom mon dow  command
*/5   *  *   *   *    /root/ops-toolkit.sh services  >> /var/log/ops-cron.log 2>&1
0     * *   *   *     /root/ops-toolkit.sh disk      >> /var/log/ops-cron.log 2>&1
30    2  *   *   *    /root/ops-toolkit.sh backup    >> /var/log/ops-cron.log 2>&1
0     8  *   *   1    /root/ops-toolkit.sh logs 10   >> /var/log/ops-weekly-report.txt 2>&1
```

Cron gotchas worth saying out loud:

- Always use **absolute paths**. Cron has a tiny `PATH` and a different working directory.
- Redirect output with `>> file 2>&1`, or errors vanish silently.
- Check it ran: `grep CRON /var/log/syslog` and `crontab -l`.
- Use `sudo crontab -e` for jobs that need root. Your user crontab cannot read `/var/log/nginx`.

## Debugging tips for when it breaks

```bash
bash -x ./ops-toolkit.sh disk        # trace every command
bash -n ./ops-toolkit.sh             # syntax check only
shellcheck ./ops-toolkit.sh          # lint (sudo apt install shellcheck)
```

## Student exercises (easy to hard)

1. Add a `memory` command that warns when used memory is above 90% (`free -m`, `awk`).
2. Add `logs` option to show only the last hour of traffic (`grep "$(date '+%d/%b/%Y:%H')"`).
3. Send a message to Slack/Discord with `curl -X POST -d ... $WEBHOOK_URL` when a service is restarted.
4. Block suspicious IPs from the report with `sudo ufw deny from <ip>`. Discuss: why must a human review this first?
5. Add a `restore` command that extracts the newest backup to `/tmp/restore-test`.

## Discussion questions

- Why do we **verify** the backup with `tar -tzf`?
- Why is `rm -rf $DIR/*` dangerous when `$DIR` is empty, and how does `set -u` help?
- Why didn't we use `set -o pipefail` in this script? (Hint: `| head` closes the pipe early.)
- What would you use instead of cron/bash once you have 100 servers? (Prometheus alerts, Ansible, systemd timers.)
