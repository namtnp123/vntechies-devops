## 1. The production case: ShopNow's bad Friday

**Company:** ShopNow, a mid-size e-commerce startup.
**Stack:** React frontend, Node.js **Product API**, Order API, PostgreSQL, Redis (the same architecture as the Lesson 6 homework).
**Team:** 6 developers and 1 DevOps engineer.

### What happened

A flash sale was due to start at 20:00. At 19:30 the team shipped a hotfix to the Product API. Four problems showed up one after another.

| # | Symptom | Root cause (in the Dockerfile) |
|---|---------|--------------------------------|
| 1 | The CI pipeline took **9 minutes** to build a one-line fix | `COPY . .` came **before** `npm install`, so the dependency layer was rebuilt on every commit |
| 2 | Each node took **3+ minutes** to pull the image, so the rolling deploy was slow and autoscaling reacted late | The image was **~1.1 GB**. It was based on the full `node:latest` and shipped compilers, dev dependencies and the `.git` folder |
| 3 | Security scan flagged **hundreds of CVEs** and a `.env` file with a live payment API key **inside the image** | No `.dockerignore`. `COPY . .` copied secrets and the whole repo into a layer, and layers are permanent |
| 4 | During the pen test, a remote-code-execution bug gave the attacker **root** in the container | No `USER` instruction, so the process ran as root. The tester then had package managers and a shell to work with |
| 5 | A "healthy" container returned 500s for 10 minutes because it had lost its DB connection | No `HEALTHCHECK`. The orchestrator only knew the process was alive |
| 6 | `docker stop` took 10 seconds and in-flight orders were dropped | App started via `npm start` (shell form), so **SIGTERM never reached Node** and Docker had to SIGKILL it |

### The lesson

> **The Dockerfile is not just a build script. It is the contract between development and operations.**
> Every line affects build speed, image size, security, reliability and cost.

The rest of this document explains how a Dockerfile works and then fixes each of those problems.

## 2. Theory: what a Dockerfile really is

### 2.1 Definition

A **Dockerfile** is a plain-text, declarative recipe. Each instruction tells the Docker builder (BuildKit) how to assemble a **container image**, which is a read-only template. Running that image produces a **container**.

```
Dockerfile  --docker build-->  Image  --docker run-->  Container
 (recipe)                   (read-only template)      (running process)
```

### 2.2 Images are layers

Every instruction that changes the filesystem (`FROM`, `RUN`, `COPY`, `ADD`) creates a **read-only layer**. Layers are:

- **Stacked**: the final image is the union of all layers.
- **Content-addressed**: identified by a hash, so identical layers are shared between images. This saves disk space and speeds up pulls.
- **Cached**: if an instruction and its inputs have not changed, Docker reuses the cached layer.
- **Immutable**: a file added in one layer and deleted in the next **still exists in the earlier layer**. This is why secrets must never be copied in. It is also why cleanup must happen in the **same** `RUN` that created the mess.

```
+-----------------------------+  <- container layer (read-write, thrown away on removal)
| writable layer              |
+-----------------------------+
| CMD / ENTRYPOINT (metadata) |  <- metadata only, no size
| COPY . .                    |  <- layer 4: your source code (changes often)
| RUN npm ci                  |  <- layer 3: dependencies (change rarely)
| COPY package*.json ./       |  <- layer 2: manifests
| FROM node:22-alpine         |  <- layer 1: base OS and runtime
+-----------------------------+
```

### 2.3 The golden rule of build cache

> **Order instructions from least-frequently-changed to most-frequently-changed.**

Once one layer is invalidated, **every layer after it is rebuilt**. This is the whole reason for the "copy `package.json` first, then install, then copy the source" pattern.

### 2.4 Build context

`docker build .` sends the directory `.` (the **build context**) to the builder. Everything in it is available to `COPY`. A large or sensitive context (`node_modules`, `.git`, `.env`) makes builds slow and risks leaking secrets. `.dockerignore` controls what is excluded.

### 2.5 Multi-stage builds

A multi-stage Dockerfile uses several `FROM` lines. Each `FROM` starts a new, independent stage. You **build** in a fat stage (compilers, dev tools) and **copy only the artifacts** into a slim final stage.

```
Stage 1 "deps"     : full toolchain  -> installs and builds
Stage 2 "runtime"  : minimal image   -> receives only built output + prod deps
Final image = Stage 2 only. Everything else is discarded.
```

### 2.6 Instruction reference

| Instruction | Creates layer? | Purpose | Build time or run time |
|-------------|:---:|---------|------------------------|
| `FROM` | yes | Choose the base image and start a stage | build |
| `ARG` | no | Build-time variable (not available at run time) | build |
| `ENV` | no (metadata) | Environment variable baked into the image and available at run time | build and run |
| `WORKDIR` | yes (dir) | Set the working directory for the following instructions | build and run |
| `COPY` | yes | Copy files from build context (or another stage) into the image | build |
| `ADD` | yes | Like `COPY` plus URL download and tar auto-extract. Prefer `COPY` | build |
| `RUN` | yes | Execute a command **while building** (install packages, compile) | build |
| `USER` | no | Set the user for the following instructions and for the container process | build and run |
| `EXPOSE` | no | **Documentation only**: declares the port the app listens on. It does not publish it | metadata |
| `VOLUME` | no | Declare a mount point for persistent data | run |
| `HEALTHCHECK` | no | Command Docker runs periodically to decide healthy or unhealthy | run |
| `ENTRYPOINT` | no | The executable that always runs | run |
| `CMD` | no | Default arguments (or default command) for the container | run |
| `LABEL` | no | Metadata (maintainer, version, source repo) | metadata |
| `STOPSIGNAL` | no | Signal sent by `docker stop` (default `SIGTERM`) | run |

### 2.7 Common confusions to clear up in class

| Confusion | Clarification |
|-----------|---------------|
| `RUN` vs `CMD` | `RUN` executes **at build time** and bakes the result into a layer. `CMD` executes **at container start**. |
| `CMD` vs `ENTRYPOINT` | `ENTRYPOINT` is the fixed program. `CMD` provides default arguments that `docker run <image> <args>` can override. |
| `ENV` vs `ARG` | `ARG` exists only during the build. `ENV` persists into the running container. **Never put secrets in either**: both are visible in `docker history` or `docker inspect`. |
| `COPY` vs `ADD` | Use `COPY` unless you really need tar auto-extraction. `ADD` from a URL is unverifiable and cache-unfriendly. |
| `EXPOSE` vs `-p` | `EXPOSE` documents. `-p 8080:3000` actually publishes the port. |
| Shell form vs exec form | `CMD npm start` (shell form) wraps the process in `/bin/sh -c`, which swallows signals. `CMD ["node","server.js"]` (exec form) makes Node PID 1 and it receives SIGTERM. **Always use exec form.** |

## 3. The "before": the Dockerfile that caused the incident

Show this to students first and ask them to **find the problems before you reveal them**.

```dockerfile
# Dockerfile.unoptimized
FROM node:latest
WORKDIR /app
COPY . .
RUN npm install
EXPOSE 3000
CMD npm start
```

Six lines, and it contains all six production problems.

| Line | Problem | Consequence |
|------|---------|-------------|
| `FROM node:latest` | Unpinned, full Debian-based image (~1 GB) | Non-reproducible builds, huge image, many CVEs |
| `COPY . .` (before install) | Invalidates cache on any file change and copies `.env`, `.git`, `node_modules` | 9-minute builds, leaked secrets |
| `RUN npm install` | Installs devDependencies, ignores the lockfile | Bloat, non-deterministic dependency versions |
| (no `USER`) | Runs as root | Container breakout and RCE impact is far worse |
| (no `HEALTHCHECK`) | Docker cannot detect a broken app | "Running" but broken containers |
| `CMD npm start` | Shell form, npm as PID 1 | SIGTERM is not forwarded, 10 s kill delay, dropped requests |

## 4. The "after": a production-grade Dockerfile

This is the sample for the Product API (Node.js). It is multi-stage, cache-friendly, non-root, health-checked and signal-safe.

```dockerfile
# syntax=docker/dockerfile:1.7

###############################################################################
# Stage 1: base - shared settings (pinned version, reproducible)
###############################################################################
ARG NODE_VERSION=22.11.0
FROM node:${NODE_VERSION}-alpine AS base
WORKDIR /app

###############################################################################
# Stage 2: deps - install ONLY production dependencies
###############################################################################
FROM base AS prod-deps
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev

###############################################################################
# Stage 3: build - full toolchain (dev deps, compiler); discarded afterwards
###############################################################################
FROM base AS build
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci
COPY . .
RUN npm run build && npm run test

###############################################################################
# Stage 4: runtime - small, non-root, the only stage that ships
###############################################################################
FROM base AS runtime

LABEL org.opencontainers.image.title="shopnow-product-api" \
      org.opencontainers.image.source="https://github.com/shopnow/product-api" \
      org.opencontainers.image.description="Product catalogue API"

ENV NODE_ENV=production \
    PORT=3000

# Copy only what we need to run, owned by the unprivileged "node" user
COPY --from=prod-deps --chown=node:node /app/node_modules ./node_modules
COPY --from=build     --chown=node:node /app/dist         ./dist
COPY --chown=node:node package.json ./

# Drop root
USER node

# Documentation of the listening port (does NOT publish it)
EXPOSE 3000

# Liveness probe that Docker / Compose can act on
HEALTHCHECK --interval=30s --timeout=3s --start-period=15s --retries=3 \
  CMD wget -qO- http://127.0.0.1:${PORT}/health || exit 1

# Exec form: node is PID 1 and receives SIGTERM directly
CMD ["node", "dist/server.js"]
```

> **Note:** `node:*-alpine` images already ship a non-root user called `node` (UID 1000), so we do not need to create one. For other base images, create one with `addgroup`/`adduser` (or `groupadd`/`useradd`).
> The `wget` command exists in Alpine through BusyBox, so no extra package is needed for the health check.

## 5. Part-by-part explanation and purpose

### 5.1 `# syntax=docker/dockerfile:1.7`

| | |
|---|---|
| **What** | Parser directive that selects the Dockerfile frontend version. It must be the very first line. |
| **Purpose** | Enables modern BuildKit features such as `RUN --mount=type=cache`. Pins the syntax so the file builds the same way everywhere. |
| **Without it** | The Docker daemon's default frontend is used and newer features may fail on older engines. |

### 5.2 `ARG NODE_VERSION=22.11.0` and `FROM node:${NODE_VERSION}-alpine AS base`

| | |
|---|---|
| **What** | `ARG` declares a build variable. `FROM` selects the base image. `AS base` names the stage. |
| **Purpose** | **Reproducibility**: a pinned version means today's build equals next month's build. **Size**: Alpine (~50 MB base) instead of Debian (~350 MB or more). **Security**: fewer packages means a smaller attack surface. **Flexibility**: bump Node with `--build-arg NODE_VERSION=22.12.0`. |
| **Production tip** | Never use `latest`. For maximum supply-chain safety, pin by digest: `node:22.11.0-alpine@sha256:...`. |
| **Trade-off** | Alpine uses musl libc. Some native modules (e.g. certain image or crypto libraries) need extra work. Use `-slim` (Debian) if you hit that. |

### 5.3 `WORKDIR /app`

| | |
|---|---|
| **What** | Sets (and creates if needed) the working directory for later instructions. |
| **Purpose** | Replaces `RUN cd /app && ...`. Gives every later `COPY`, `RUN` and `CMD` a predictable root. |

### 5.4 The `prod-deps` stage: `COPY package*.json` then `npm ci --omit=dev`

| | |
|---|---|
| **What** | Copy **only** the dependency manifests, then install production dependencies. |
| **Purpose** | **Cache efficiency**: this layer is rebuilt **only when the manifests change**, not on every code change. That takes the 9-minute build to well under a minute in CI when only source code changed. |
| **`npm ci` vs `npm install`** | `npm ci` installs exactly what `package-lock.json` says and fails if they disagree. This gives deterministic, repeatable builds. It is faster and designed for CI. |
| **`--omit=dev`** | Excludes test frameworks, linters and compilers from the shipped `node_modules`. This is often the single biggest size win. |
| **`--mount=type=cache,target=/root/.npm`** | A BuildKit cache mount. The npm download cache persists between builds but is **not stored in the image**. |

### 5.5 The `build` stage

| | |
|---|---|
| **What** | Installs **all** dependencies (including dev), copies the source, compiles (`npm run build`) and runs tests. |
| **Purpose** | Compilation and testing need heavy tooling, which we do not want in production. Running tests here means **a failing test fails the image build**, so a broken image can never be pushed. |
| **Key idea** | This stage may be 500 MB. It does not matter, because **none of it is shipped** except what we explicitly copy out. |
| **Cache note** | `COPY . .` comes **after** `npm ci`, so source edits do not trigger a reinstall. |

### 5.6 The `runtime` stage: `FROM base AS runtime`

| | |
|---|---|
| **What** | A fresh stage that starts again from the small base. |
| **Purpose** | This is the **only** stage that becomes the final image. Compilers, dev dependencies, test files, source maps and the npm cache are all left behind. |

### 5.7 `LABEL`

| | |
|---|---|
| **What** | Key-value metadata stored in the image. |
| **Purpose** | Traceability: which repo and version built this image? Useful for registries, scanners and audits. The `org.opencontainers.image.*` keys are the standard names that tools understand. |

### 5.8 `ENV NODE_ENV=production PORT=3000`

| | |
|---|---|
| **What** | Environment variables stored in the image and visible at run time. |
| **Purpose** | `NODE_ENV=production` makes Express and many libraries enable optimisations and disable verbose debug behaviour. `PORT` is a safe **default**. It can be overridden with `-e PORT=...` or in Compose. |
| **Rule** | Use `ENV` for non-sensitive defaults only. **Secrets are injected at run time** (Docker secrets, a vault, or Kubernetes Secrets), never baked in. |

### 5.9 `COPY --from=... --chown=node:node`

| | |
|---|---|
| **What** | `--from=<stage>` copies files out of an earlier stage. `--chown` sets the owner during the copy. |
| **Purpose** | This is the moment multi-stage pays off: copy `node_modules` (prod only) and `dist` (compiled) and **nothing else**. `--chown` avoids a separate `RUN chown -R`, which would duplicate every file into another layer and increase the image size. |

### 5.10 `USER node`

| | |
|---|---|
| **What** | All following instructions, and the container's main process, run as UID 1000 instead of root. |
| **Purpose** | **Least privilege.** If an attacker gets code execution, they cannot install packages, modify system files or easily escape to the host. This is a core requirement of most security baselines (CIS Docker Benchmark, Kubernetes Pod Security Standards). |
| **Placement** | Put it **after** steps that need root (installing OS packages) and **before** `CMD`. |
| **Gotcha** | Non-root users cannot bind ports below 1024. This is why the app listens on `3000` and a reverse proxy or the `-p` flag maps it to 80 or 443. |

### 5.11 `EXPOSE 3000`

| | |
|---|---|
| **What** | Metadata that says "this container listens on 3000". |
| **Purpose** | Documentation for humans and tools (e.g. `docker run -P` publishes all exposed ports to random host ports). |
| **Common mistake** | Believing it opens the port to the host. It does not. You must publish with `-p host:container` or Compose `ports:`. |

### 5.12 `HEALTHCHECK`

| | |
|---|---|
| **What** | Docker runs the command inside the container on a schedule. Exit code 0 means healthy and 1 means unhealthy. |
| **Parameters** | `--interval` (how often), `--timeout` (max duration of one check), `--start-period` (grace time while the app boots, failures are not counted), `--retries` (consecutive failures before "unhealthy"). |
| **Purpose** | Detects an app that is running but broken (lost DB connection, deadlock). It powers `depends_on: condition: service_healthy` in Compose and restart or replace decisions in Swarm. It also feeds `docker ps` status. |
| **Design advice** | Make `/health` check real dependencies (a quick DB `SELECT 1`, Redis `PING`) but keep it fast and cheap. In Kubernetes, `HEALTHCHECK` is ignored and you define liveness and readiness probes instead. The idea is the same. |

### 5.13 `CMD ["node", "dist/server.js"]`

| | |
|---|---|
| **What** | The default command run when the container starts, in **exec form** (JSON array). |
| **Purpose** | Node becomes **PID 1** and receives `SIGTERM` from `docker stop`, so it can close the HTTP server and DB pool gracefully (finish in-flight orders). With `CMD npm start`, the signal goes to `/bin/sh` or npm and Node is killed with SIGKILL after 10 seconds. |
| **Why not `npm start`** | npm adds an extra process, extra memory and signal-handling problems. |
| **Graceful shutdown** | Your app should handle it: `process.on('SIGTERM', () => server.close(...))`. If your app spawns children or does not reap zombies, add `tini` (`docker run --init` or `ENTRYPOINT ["/sbin/tini","--"]`). |

### 5.14 Instruction order recap (why this order)

```
FROM            rarely changes     \
ARG/ENV         rarely changes      |  top = cached for months
COPY manifests  changes weekly      |
RUN npm ci      (follows manifests)/
COPY source     changes every commit  <- placed LAST so only this layer rebuilds
USER/HEALTHCHECK/CMD  metadata, cost nothing
```

## 6. Supporting files: .dockerignore and Compose

### 6.1 `.dockerignore` (fixes problem #3)

A Dockerfile alone is not enough. This file keeps the build context small and secrets out of layers.

```gitignore
# .dockerignore
.git
.gitignore
node_modules
npm-debug.log
dist
coverage
.env
.env.*
!.env.example
Dockerfile*
docker-compose*.yml
*.md
.vscode
.idea
```

**Purpose:** a smaller context means faster builds, no accidental secrets, and cache stability (changing a README no longer invalidates `COPY . .`).

### 6.2 `docker-compose.prod.yml` (the container in its runtime environment)

The Dockerfile describes **what the image is**. Compose (or Kubernetes) describes **how it runs**.

```yaml
services:
  product-api:
    build:
      context: ./product-api
      args:
        NODE_VERSION: "22.11.0"
    image: registry.shopnow.io/product-api:1.4.2   # immutable version tag, never "latest"
    restart: unless-stopped
    environment:
      NODE_ENV: production
      PORT: "3000"
      DB_HOST: postgres
      REDIS_HOST: redis
    secrets:
      - db_password                                  # injected at run time, not in the image
    networks:
      - backend
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started
    deploy:
      resources:
        limits:
          cpus: "0.50"
          memory: 256M
    read_only: true                                  # immutable root filesystem
    tmpfs:
      - /tmp
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
    # No "ports:" - only the reverse proxy on the frontend network is public

  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 3s
      retries: 5

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    networks:
      - backend

networks:
  backend:
    internal: true          # no route to the outside world
  frontend: {}

volumes:
  pgdata:

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

> Note the cross-over: the Dockerfile `USER node`, the Compose `read_only`, `cap_drop` and `no-new-privileges` are **defence in depth**. The image is safe by construction, and the runtime adds extra restrictions.

## 7. Build, run and verify (demo script)

Run these live in class. They use the commands from Lesson 5's cheat sheet and Lesson 6's lab.

```bash
# 0. Build both versions from the same source
docker build -f Dockerfile.unoptimized -t product-api:unoptimized .
docker build -t product-api:optimized .

# 1. Compare sizes   (the "wow" moment)
docker images product-api

# 2. Inspect layers and see where size comes from
docker history product-api:unoptimized
docker history product-api:optimized
# Optional: explore interactively with dive
dive product-api:optimized

# 3. Prove the cache works: change one source file and rebuild
echo "// tweak" >> src/server.js
time docker build -t product-api:optimized .
# -> "CACHED" appears for the dependency layers; only the later layers rebuild

# 4. Prove it runs as non-root
docker run -d --name api -p 3000:3000 product-api:optimized
docker exec api whoami                 # -> node   (unoptimized shows: root)
docker exec api id                     # -> uid=1000(node)

# 5. Watch the health check work
docker ps                              # STATUS: Up 20s (healthy)
docker inspect --format '{{json .State.Health}}' api | jq

# 6. Prove graceful shutdown
time docker stop api                   # optimized: ~instant, unoptimized: ~10 s

# 7. Prove no secrets leaked
docker run --rm product-api:unoptimized ls -a /app    # shows .env and .git  (bad)
docker run --rm product-api:optimized   ls -a /app    # clean

# 8. Security and lint
docker scout cves product-api:optimized      # or: trivy image product-api:optimized
hadolint Dockerfile

# 9. Clean up
docker rm -f api
docker image prune
```

## 8. Before vs after

> The numbers below are **typical for a mid-size Node.js API** and are meant as expectations to compare against. Have students measure their own and record them in `optimization-report.md` (Lesson 6 homework, Exercise 2).

| Metric | Unoptimized | Optimized | Why |
|--------|-------------|-----------|-----|
| Image size | ~1.0-1.2 GB | ~120-180 MB | Alpine, prod-only deps, multi-stage |
| Rebuild after a code change | minutes | seconds | Layer order and cache mount |
| Pull time per node | minutes | seconds | Fewer bytes to transfer |
| Known CVEs (scan) | hundreds | a handful | Minimal base, no extra packages |
| Runs as | root | UID 1000 | `USER node` |
| Secrets in image | yes (`.env`) | none | `.dockerignore` and run-time secrets |
| `docker stop` time | ~10 s (SIGKILL) | <1-2 s (graceful) | Exec-form `CMD` |
| Broken-app detection | none | automatic | `HEALTHCHECK` |
| Reproducible build | no (`latest`, `npm install`) | yes (pinned, `npm ci`) | Version pinning and lockfile |

**Business outcome for ShopNow:** faster hotfixes (minutes, not tens of minutes), faster autoscaling during sales, a clean security audit, and zero dropped orders during deploys.

## 9. Production checklist

Use this as a review checklist for any Dockerfile (also a handy rubric for homework grading).

**Base image**
- [ ] Pinned version tag (or digest), never `latest`
- [ ] Minimal variant (`alpine`, `slim`, `distroless`)
- [ ] From a trusted source (Docker Official Image or verified publisher)

**Build**
- [ ] Multi-stage build; only runtime artifacts reach the final stage
- [ ] Dependency manifests copied and installed **before** source code
- [ ] Lockfile-based install (`npm ci`, `pip install -r` with hashes, `go mod download`)
- [ ] Dev dependencies excluded from the final image
- [ ] `.dockerignore` present
- [ ] Related shell commands merged into one `RUN`, with cleanup in the same layer
- [ ] Tests run in the build or in CI before the image is published

**Security**
- [ ] Non-root `USER`
- [ ] No secrets in `ENV`, `ARG`, `COPY` or any layer
- [ ] No unnecessary packages, shells or tools in the final image
- [ ] Image scanned (Trivy, Docker Scout) and Dockerfile linted (Hadolint)
- [ ] Runtime hardening: `read_only`, `cap_drop: [ALL]`, `no-new-privileges`

**Operations**
- [ ] Exec-form `CMD` or `ENTRYPOINT` (correct signal handling)
- [ ] `HEALTHCHECK` defined
- [ ] Configuration through environment variables (twelve-factor)
- [ ] Logs written to **stdout and stderr**, not to files inside the container
- [ ] Resource limits and restart policy set in Compose or the orchestrator
- [ ] Immutable, versioned image tags (e.g. semver or git SHA)
- [ ] `LABEL` metadata for traceability

## 10. Common mistakes and discussion questions

### Common mistakes (ask students to spot them)

| Mistake | Fix |
|---------|-----|
| `RUN apt-get update` and `RUN apt-get install` as separate lines | Combine: `RUN apt-get update && apt-get install -y --no-install-recommends pkg && rm -rf /var/lib/apt/lists/*` |
| Deleting a file in a later `RUN` to "save space" | The file still lives in the earlier layer. Never add it, or use a multi-stage build. |
| `COPY . .` as the first instruction | Copy manifests, install, then copy source. |
| Using `ENV DB_PASSWORD=...` | Inject at run time with secrets. |
| Using `chmod -R` or `chown -R` in a separate `RUN` | Use `COPY --chown` or `COPY --chmod` to avoid duplicating layers. |
| Using `ADD` for local files | Use `COPY`. |
| Running SSH or multiple processes in one container | One main process per container. Use Compose or Kubernetes for the rest. |
| Storing database data inside the container | Use named volumes (Lesson 5 homework: WordPress and MySQL persistence). |

### Discussion questions

1. If you delete `node_modules` at the end of a `RUN`, why does the image not shrink?
2. Two services share the same `node:22.11.0-alpine` base. How many times is the base layer stored on a host, and why?
3. Why can a container be `Up` in `docker ps` but still be broken? What closes that gap?
4. When would you pick `distroless` over `alpine`? What do you lose (shell access, debuggability)?
5. A teammate says "the CI pipeline pushes `latest`, so it's always up to date." Give three reasons that is dangerous in production.
6. The Dockerfile has `USER node` but Compose also has `read_only: true`. Is one redundant? Explain defence in depth.

### Key takeaways for students

1. **A Dockerfile is code.** Review it, lint it and version it like any other code.
2. **Layers are permanent and cached.** Order matters, and secrets in any layer are forever.
3. **Multi-stage builds** separate "what I need to build" from "what I need to run".
4. **Least privilege**: small base, non-root user, no secrets, no extra tools.
5. **Operability** is part of the image: health checks, signal handling and stdout logging.
