# Docker Fundamentals — Explained

> Companion notes for **2. Slide - Docker Fundamentals.pdf**.
> Audience: people already working in IT — help desk, support, development, DevOps — who have not used Docker yet.
> Assumes you know what an OS, process, port, IP address, server and dependency are. Does not assume any container knowledge.

---

## 1. The problem, stated precisely

Everyone in IT has met this failure: the application runs on the developer's machine and fails on the server, or works in staging and breaks in production, with no code change.

The usual causes are boring and specific:

- Different interpreter or runtime version (`python3.11` vs `python3.8`).
- A system library at a different version (`glibc`, `libssl`, `libstdc++`).
- A missing OS package (`ca-certificates`, `tzdata`, `curl`) that happened to be installed on one machine.
- A different locale or timezone.
- Configuration baked into a machine by hand months ago, undocumented.
- Two applications on the same host that need conflicting versions of the same library.

The old answer is a setup runbook and a configuration management tool. Both work, and both drift. The machine accumulates history, and the history is not written down anywhere.

Docker's answer is different in kind, not degree: **stop reconstructing the environment on each host, and ship the environment as an artifact.**

That artifact is the image. Running it produces a container.

---

## 2. Containerization

A container packages an application together with its userland dependencies — runtime, libraries, OS packages, files — into a single portable artifact that runs identically anywhere a compatible kernel exists.

The name comes from freight. Standardised steel containers let cranes, ships, trains and trucks handle any cargo without knowing what is inside. Standardisation is the whole value: the interfaces are fixed, so the contents stop mattering to everything downstream. Docker applies the same trick to software — one image format, one runtime interface, any host.

### Why it is adopted

**Portability.** The same image digest produces the same behaviour on a laptop, in CI, and in production. "Works on my machine" stops being a category of bug.

**Efficiency.** A container is a process, not a booted OS. Start time is milliseconds; memory overhead is the process itself plus a small amount of runtime bookkeeping. Density per host is an order of magnitude better than VMs.

**Isolation.** Each container has its own filesystem view, network stack, process tree and user namespace. Two applications with conflicting dependency versions coexist without interference.

**Immutability and scalability.** A container is disposable and replaceable. Scaling means starting more of the same image, not installing software on another host. This is also the substrate for microservices and for reproducible CI.

### What it is not

A container is not a security boundary equivalent to a VM. It shares the host kernel; a kernel privilege-escalation bug is shared by every container on that host. For multi-tenant untrusted workloads, VMs or sandboxed runtimes (gVisor, Kata) are the appropriate tool. For your own workloads, containers are fine and this distinction is usually over-stated — but it should be stated.

---

## 3. What a container actually is

This is the part worth understanding properly, because it removes the mystery from every later behaviour.

**A container is one or more Linux processes with restricted views of the system.** No emulation, no second kernel, no hypervisor. On Linux, four kernel features do the work:

| Kernel feature | What it restricts | Practical effect |
| --- | --- | --- |
| **Namespaces** | what a process can *see* | its own PID tree, network interfaces, mount points, hostname, users, IPC |
| **cgroups** | what a process can *use* | CPU and memory limits, I/O throttling, process count |
| **chroot / pivot_root** | where its filesystem root is | it sees the image's filesystem, not the host's |
| **capabilities + seccomp** | what syscalls it may make | root inside the container is not root on the host |

So when you run `nginx` in a container:

- `ps` inside shows nginx as PID 1. On the host, that same process has an ordinary PID like 34812.
- `ip a` inside shows `eth0` at `172.17.0.2`. On the host it is a `veth` pair plugged into a bridge.
- `whoami` inside may say `root`. On the host it maps to an unprivileged UID (unless you configured otherwise).
- `df -h` inside shows the image's filesystem, not your disk layout.

That is the entire trick. It is why start-up is instant: nothing boots. It is why the image can be 5 MB while a VM image is 2 GB: there is no OS inside.

On Windows and macOS, Docker cannot do this natively, because the host kernel is not Linux. Docker Desktop runs a small Linux VM and containers run inside it. This has one practical consequence worth knowing: bind-mount I/O on macOS and Windows goes through that VM boundary and is significantly slower than on Linux.

### Containers versus virtual machines

| | Virtual machine | Container |
| --- | --- | --- |
| Isolation unit | hardware virtualisation, own kernel | kernel namespaces, shared kernel |
| Boot | firmware → kernel → init → services | none; process starts directly |
| Start time | 20 s – 2 min | < 1 s |
| Image size | GBs | MBs |
| Memory overhead | guest OS, typically 512 MB+ | process RSS + small overhead |
| Density per host | single digits to low tens | dozens to hundreds |
| Kernel choice | any OS | must match host kernel family |
| Security boundary | strong | weaker; shared kernel |
| Good for | different OS, untrusted tenants, legacy apps | services, CI, reproducible builds |

The common analogy, which is accurate enough: a VM is a separate house with its own utilities; a container is an apartment sharing the building's plumbing but with its own locked door.

## 4. Images and containers

**Image** — an immutable, layered filesystem plus metadata (entrypoint, environment, exposed ports, user). Read-only. Not runnable by itself.

**Container** — a process created from an image, plus one thin writable layer on top, plus the namespace and cgroup configuration.

The relationship is class to object, or recipe to dish. One image, many containers.

### Layers and copy-on-write

An image is a stack of layers. Each Dockerfile instruction that changes the filesystem creates one layer. Layers are content-addressed and shared:

- `nginx:latest` and `nginx:alpine` share layers where their contents match.
- Ten containers from one image share the same read-only layers on disk. Only the writable layer is per-container.

Writes go to the writable layer, using copy-on-write: modifying `/etc/nginx/nginx.conf` copies that one file up, leaving the image layer untouched. Deleting a file in a lower layer writes a whiteout marker, it does not reclaim space.

Two consequences you will meet in practice:

1. **Image size is dominated by layers you did not write.** The base image matters more than your application.
2. **Data written in the writable layer dies with the container.** This is by design; see section 6.

### Tags are not versions you can trust

`nginx:latest` is not "the newest nginx" in any guaranteed sense; it is whatever the maintainer last pushed to that tag. Tags are mutable pointers. For reproducibility, pin a digest:

```bash
docker pull nginx@sha256:8a1b...   # immutable
docker image inspect nginx:1.25 --format '{{index .RepoDigests 0}}'
```

### Building an image

A Dockerfile is a list of instructions executed in order, each producing a layer.

```dockerfile
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*
COPY app.sh /usr/local/bin/app.sh
RUN chmod +x /usr/local/bin/app.sh
USER 1000
ENTRYPOINT ["/usr/local/bin/app.sh"]
```

```bash
docker build -t my-app:1.0.0 .
```

`-t` sets `name:tag`. The trailing `.` is the **build context** — the directory sent to the daemon; `COPY` can only see files inside it. Build cache: an instruction re-runs only if its inputs changed, which is why `COPY package.json` before `COPY .` is the standard Node pattern.

In this lesson the deck only introduces "base image + your steps = your image". Dockerfile authoring is covered properly in a later lesson.

## 5. Architecture

```
   docker CLI
      │  REST over /var/run/docker.sock (or TCP+TLS)
      ▼
   dockerd ──── image store, container store, networks, volumes
      │
      ▼
   containerd ──► runc ──► container process
      │
      └── pulls from registry (Docker Hub, GHCR, ECR, Harbor, ...)
```

**Client** — the `docker` binary. It parses your command, turns it into an HTTP request, and prints the response. It holds no state and does no work. That is why `docker` on your laptop can manage a daemon on another host (`-H ssh://server`), and why every command fails when the daemon is down.

**Daemon (`dockerd`)** — the long-running service. Owns images, containers, networks, volumes, and the API. Runs as root on Linux.

**containerd / runc** — the layers below. `dockerd` delegates container lifecycle to `containerd`, which invokes `runc` to create the namespaces and start the process. This is why Docker can run Kubernetes-style workloads and why the OCI standards exist: images and runtimes are specified independently of Docker.

**Registry** — an HTTP API serving image manifests and layers. Docker Hub is the default; the same protocol runs GHCR, ECR, GCR, Harbor, Nexus. `pull` is a read, `push` is a write. Public by default on Hub — never bake credentials into an image, and note that anyone can pull what you push publicly.

**Objects** — images, containers, networks, volumes. Networks and volumes get their own sections below.

## 6. Running containers: reading the command line

```bash
docker run -d --name web -p 8080:80 -e TZ=Asia/Ho_Chi_Minh \
  -v webdata:/usr/share/nginx/html --restart unless-stopped nginx:1.25-alpine
```

| Flag | Meaning |
| --- | --- |
| `-d` | detached — do not attach to the process's stdio |
| `--name` | stable name; otherwise Docker generates one |
| `-p 8080:80` | publish `hostPort:containerPort`; binds `0.0.0.0` unless you write `-p 127.0.0.1:8080:80` |
| `-e` | environment variable, the standard configuration mechanism |
| `-v name:/path` | named volume (a host path here instead would be a bind mount) |
| `--restart` | restart policy: `no`, `on-failure`, `always`, `unless-stopped` |
| `--rm` | delete the container when it exits — use for one-off jobs |

**`-p` is a port forward, not a firewall rule.** `-p 8080:80` makes Docker listen on the host and forward to the container's port 80. Binding to `0.0.0.0` exposes it on every interface, including the network — a common accidental exposure. Bind to `127.0.0.1` when it should stay local.

**`-it`** is two flags: `-i` keeps stdin open, `-t` allocates a pseudo-terminal. You need both for an interactive shell, and neither for a service.

### Lifecycle

```
created ──start──► running ──stop──► exited ──rm──► deleted
                     │  ▲                │
                     │  └────start───────┘
                     └──pause──► paused
```

```bash
docker create nginx                 # created, not started
docker start web / docker stop web  # stopped containers keep their writable layer
docker restart web
docker pause web / docker unpause web
docker rm web                       # must be stopped; -f forces
docker rm -f web
```

`docker stop` sends SIGTERM, waits 10 seconds, then SIGKILL. If your app needs longer to shut down cleanly, `docker stop -t 30`. If it ignores SIGTERM, it is being killed hard and you are losing data — fix the app, not the timeout.

### Inspecting

```bash
docker ps                       # running only
docker ps -a                    # including exited — this is the one you want when something is "missing"
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
docker logs -f --tail 100 web   # follow, last 100 lines
docker logs --since 10m web
docker inspect web              # full JSON: IP, mounts, env, state, exit code
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' web
docker stats                    # live CPU/memory/IO per container
docker exec -it web sh          # a shell in a running container
docker top web                  # host-side process list for the container
docker port web                 # what is actually published
docker diff web                 # files changed in the writable layer
```

`docker exec` requires a **running** container. `docker run` creates a new one. Students mix these up for weeks; the error message `container is not running` is the giveaway.

`docker exec` also needs a shell to exist in the image. `alpine` and `distroless` images may have `sh` but no `bash` — use `sh`, or skip exec entirely and read logs.

### Cleanup

```bash
docker rm web                   # one container
docker rm $(docker ps -aq)      # all stopped
docker rmi nginx:1.25-alpine    # image; fails if a container still references it
docker image prune              # dangling layers
docker system prune -a --volumes  # everything unused, INCLUDING volumes — destructive, read twice
docker system df                # where the disk actually went
```

`docker system prune --volumes` deletes volumes not attached to a container. That is how people lose databases. There is no undo.

## 7. Storage

The container's writable layer is destroyed with the container. Anything that must outlive it goes outside.

| | Bind mount | Named volume | tmpfs |
| --- | --- | --- | --- |
| Syntax | `-v /host/path:/ctr/path` | `-v name:/ctr/path` | `--tmpfs /ctr/path` |
| Location | an exact host path | `/var/lib/docker/volumes/<name>/_data` | RAM |
| Managed by Docker | no | yes | n/a |
| Survives container removal | yes, while the host path exists | yes, until `volume rm` | no |
| Survives host reboot | yes | yes | no |
| Portable across hosts | no | yes, via backup/restore or drivers | no |
| Typical use | source code, config in development | databases, uploads, app state | secrets, scratch, cache |

**Bind mount** — the container sees a real host directory. Two-way, immediate. Right for development and for handing config files in. Wrong for portability: it depends on host layout, and UID/GID mismatches cause the classic "permission denied" when the container's user differs from the file owner. On macOS/Windows it is slow, as noted earlier.

**Named volume** — Docker owns the directory and its metadata. Portable, permission-sane, the correct choice for stateful services. Back it up with a throwaway container:

```bash
docker run --rm -v dbdata:/data -v "$PWD":/backup alpine \
  tar czf /backup/dbdata.tar.gz -C /data .
```

**tmpfs** — memory only, never written to disk. Correct for tokens and credentials, and for scratch space where disk I/O would be wasted.

Read-only mounts are a useful hardening step: `-v /host/config:/etc/app:ro` stops the container writing to your config.

Two details that cause real incidents:

- **Deleting a container does not delete its named volumes** unless you pass `-v` to `docker rm`. Old volumes accumulate silently; `docker system df -v` shows them.
- **A volume is only initialised from the image the first time it is created.** If you mount an empty volume over a directory the image populated, the image's files are hidden, not merged.

## 8. Networking

Docker creates virtual networks and attaches containers to them. A container gets its own network namespace: its own interfaces, routing table and DNS configuration.

### Drivers you will actually use

**bridge** (default, and the one to use)

```bash
docker network create appnet
docker run -d --name db  --network appnet -e MYSQL_ROOT_PASSWORD=... mysql:8.0
docker run -d --name web --network appnet -p 8000:80 wordpress
```

- Each container gets an address on the bridge subnet, typically `172.x.0.0/16`.
- Containers on the same network reach each other by **name** — Docker runs an embedded DNS server at `127.0.0.11` and registers container names and aliases.
- Outbound traffic is NATed through the host.
- **Name resolution only works on user-defined networks.** The default `bridge` network has no DNS: containers there can only reach each other by IP, and those IPs change on restart. This is the single most common networking mistake — always create your own network.

**host**

```bash
docker run -d --network host nginx
```

The container shares the host's network namespace directly. No NAT, no port mapping, no isolation, best throughput. Port conflicts are yours to manage: two containers cannot both bind 80. Common in performance-sensitive setups and in some monitoring agents.

**none**

```bash
docker run --network none alpine ip a     # only lo
```

Loopback only. For batch jobs and anything that must not reach the network.

Others exist (`overlay` for Swarm, `macvlan`/`ipvlan` for L2 presence on the physical network) and are out of scope here.

### The localhost trap

Inside a container, `127.0.0.1` is **the container itself**, not the host. An application configured to reach a database at `localhost:3306` will fail when both run in separate containers — they are separate network namespaces.

Fix: use the service name (`db:3306`) on a shared user-defined network. If you genuinely need the host from inside a container, `host.docker.internal` works on Docker Desktop, and `--add-host=host.docker.internal:host-gateway` on Linux.

### Summary

| Mode | Outbound internet | Reachable from host/network | Isolation | DNS by name |
| --- | --- | --- | --- | --- |
| `bridge` (user-defined) | yes, via NAT | only through `-p` | good | yes |
| `bridge` (default) | yes, via NAT | only through `-p` | good | **no** |
| `host` | yes, direct | yes, direct | none | n/a |
| `none` | no | no | total | n/a |

## 9. What this means for your role

**Help desk / support.** Docker explains a class of tickets you already see: "the service is down" is often `docker ps -a` showing `Exited (1)`, and `docker logs` giving the reason in ten seconds. Learn `ps -a`, `logs --tail`, `inspect -f '{{.State.ExitCode}}'`, and `stats`. You will also handle "disk full" on Docker hosts — almost always images and volumes, visible with `docker system df`.

**Development.** The image is the deliverable, not the source tree. Build locally, run the same image in CI, ship the same digest. Understand layer caching, keep the build context small, never `COPY . .` before installing dependencies, and use bind mounts for the edit-refresh loop.

**DevOps.** Containers are the unit of deployment. You care about restart policies, healthchecks, resource limits (`--memory`, `--cpus`), log drivers, image scanning, registry lifecycle, and pinning digests. Compose and Kubernetes build on exactly the primitives above — nothing new, just orchestration of many containers.

## 10. Troubleshooting table

| Symptom | Likely cause | Check |
| --- | --- | --- |
| Container exits immediately | entrypoint finished or crashed | `docker logs <c>`, `docker inspect -f '{{.State.ExitCode}}' <c>` |
| `Exited (137)` | SIGKILL — OOM or `stop` timeout | `docker inspect -f '{{.State.OOMKilled}}' <c>` |
| `Exited (1)` | application error | `docker logs <c>` |
| `port is already allocated` | host port in use | `docker ps --format '{{.Names}} {{.Ports}}'`, `lsof -i :8080` |
| Connection refused from browser | bound to `127.0.0.1`, or wrong host port | `docker port <c>`, `docker inspect -f '{{json .NetworkSettings.Ports}}' <c>` |
| App cannot reach another container by name | not on a user-defined network, or using `localhost` | `docker inspect -f '{{json .NetworkSettings.Networks}}' <c>` |
| `permission denied` on docker.sock | user not in `docker` group | `groups`, `sudo usermod -aG docker $USER` then re-login |
| `exec` says container is not running | it exited | `docker ps -a` |
| `exec` says executable not found | no `bash` in the image | use `sh` |
| Data gone after recreate | written to the writable layer | check `-v`, `docker inspect -f '{{json .Mounts}}' <c>` |
| Disk full on host | images, volumes, build cache | `docker system df -v`, then prune deliberately |
| Pull fails with rate limit | Docker Hub anonymous pull limit | authenticate with `docker login` |
| Slow file access on macOS | bind mount through the Docker Desktop VM | accept it, or use a volume |

## 11. Glossary

| Term | Meaning |
| --- | --- |
| Image | immutable layered filesystem + metadata; the artifact |
| Container | process + writable layer + namespace/cgroup config, created from an image |
| Dockerfile | build instructions, one layer per filesystem-changing instruction |
| Layer | content-addressed filesystem diff, shared between images |
| Tag / digest | mutable human label / immutable content hash |
| Registry | HTTP store of manifests and layers |
| Daemon | `dockerd`, owns all objects, exposes the API |
| Volume | Docker-managed persistent storage, survives container removal |
| Bind mount | host path mapped into the container |
| tmpfs | memory-backed mount, non-persistent |
| Bridge network | private virtual L2/L3 network with NAT and (if user-defined) DNS |
| Publish (`-p`) | host-side port forward into a container |
| Writable layer | per-container upper filesystem layer, discarded on removal |

## 12. Check yourself

1. Two containers from the same image — how much disk do the image layers take?
   *Once. Layers are shared read-only; only writable layers are per-container.*

2. `docker stop` then `docker start` — is the data still there? `docker rm`?
   *Yes after stop/start, same container. No after rm, unless it was in a volume or bind mount.*

3. Why does name-based service discovery fail on the default bridge network?
   *The embedded DNS server only exists on user-defined networks.*

4. What does `-p 8080:80` do at the OS level?
   *Docker installs a NAT rule; the host listens on 8080 and forwards to the container's 80.*

5. Why is a container not equivalent to a VM for isolation?
   *It shares the host kernel; namespaces restrict visibility, not kernel vulnerabilities.*

6. `docker ps` shows nothing after `docker run hello-world`. Why?
   *The process finished and exited. `docker ps -a` shows it.*

7. Which is correct for a database — bind mount or named volume? Why?
   *Named volume: Docker manages permissions and location, it is portable and survives removal.*

8. What is the build context, and why does its size matter?
   *The directory sent to the daemon on `docker build`; large contexts slow every build.*
